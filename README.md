# IT Asset Lifecycle Management

A portfolio-ready, read-only proof of concept demonstrating IT asset governance, lifecycle validation, warranty exposure, and rules-based technology refresh prioritization using synthetic data.

> **Scope:** This is a demonstration project, not a production ITAM platform. It does not connect to endpoint-management, procurement, finance, identity, CMDB, or ITSM systems. It does not make procurement or retirement decisions.

## What it demonstrates

- A structured asset register with ownership, location, lifecycle, warranty, criticality, and estimated replacement cost.
- Data-quality checks for duplicate IDs, missing ownership, invalid lifecycle states, and missing core fields.
- Rules-based risk scoring with explainable factors and recommended review actions.
- Refresh planning that considers criticality, support status, warranty, age, and condition—not age alone.
- CSV outputs suitable for analysis and executive reporting.
- Automated unit tests and a GitHub Actions test workflow.

## Quick start

Requires Python 3.10+; no third-party packages are needed.

```bash
python -m venv .venv
# Windows PowerShell:
.venv\\Scripts\\Activate.ps1
# macOS/Linux:
# source .venv/bin/activate

python -m itam.cli --input data/assets.csv --output-dir reports
python -m unittest discover -s tests -v
```

Expected output files:

- `reports/asset_assessment.csv` — asset-level scores, findings, and recommendations.
- `reports/data_quality_issues.csv` — register quality exceptions.
- `reports/executive_summary.json` — counts and estimated refresh exposure.

The report is deterministic for a given input and `--as-of` date.

## Example findings

The bundled sample data is synthetic. It intentionally includes cases such as an unsupported critical network device, expiring warranties, missing ownership, and an asset marked retired but still recorded as deployed. The exact output is generated by the program.

## Scoring approach

The score is a **review-priority indicator**, not a probability of failure and not a financial valuation. Rules add points for factors such as:

- Critical asset with vendor support ended
- Warranty expired or nearing expiration
- Planned refresh date passed
- Condition marked poor
- Missing ownership or lifecycle inconsistencies

Risk bands: `HIGH` (50+), `MEDIUM` (25–49), and `LOW` (0–24). The threshold values are illustrative and should be calibrated to organizational policy before any operational use. A high-priority individual finding must not be hidden by an aggregate score.

## Lifecycle states

`REQUESTED → ORDERED → RECEIVED → IN_SERVICE → REPAIR → RETIRED`

Transitions are a reference workflow, not an enforced change-control engine. Retirement requires separate approval and secure data sanitization procedures in a real environment.

## Data dictionary

| Field | Description |
|---|---|
| `asset_id` | Unique organization-assigned identifier |
| `asset_type` | Laptop, server, network device, etc. |
| `manufacturer`, `model`, `serial_number` | Product and identity details |
| `assigned_to`, `owner`, `business_unit`, `location` | Accountability and placement |
| `purchase_date`, `warranty_end`, `planned_refresh_date` | Lifecycle milestones (`YYYY-MM-DD`) |
| `lifecycle_status` | Current lifecycle state |
| `criticality` | `LOW`, `MEDIUM`, or `HIGH` |
| `condition` | `GOOD`, `FAIR`, or `POOR` |
| `vendor_support_status` | `SUPPORTED` or `ENDED` |
| `replacement_cost_estimate` | Synthetic planning estimate; not a quote or approved budget |

## Governance principles

1. Treat authoritative inventory sources as systems of record.
2. Assign a business or technical owner to every in-service asset.
3. Reconcile asset records regularly against approved inventory sources.
4. Define ownership, evidence, and approval requirements for lifecycle transitions.
5. Use risk-based prioritization; age alone does not determine replacement.
6. Protect personal, financial, and infrastructure data in production systems.
7. Require approval and audit trails for procurement, reassignment, retirement, and disposal.
8. Validate data and thresholds before integrating with CMDB or ITSM workflows.
